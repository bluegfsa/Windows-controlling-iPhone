> 用法：先看下面这张速查表；找不到再往下读细节。**排障第一动作永远是 `phone.cmd doctor`**——它的 `fix` 字段通常直接给答案。

## 1. libusb0 UpperFilter：最隐蔽的一个坑

**症状链**：`ios list` 空 → 以为是 usbuxd 没起 → 以为 USB 被独占 → 其实都不对。

真相：装过 iPhoneMirror / 爱思助手的"反控"后，Apple 复合设备（`USB\VID_05AC&PID_12A8\...`）被挂了 `libusb0` **UpperFilter**。设备节点还在，但从 usbmux 的枚举路径里被摘掉了。

- usbmuxd 其实是正常的（27015 在监听）
- 注册表 `Enum\...\Device Parameters\UpperFilters` 受 PnP 保护，`SetValue` **会被拒绝**
- 唯一可靠解法：`pnputil /remove-device "<instance id>"`，然后**物理拔插数据线**，让 Windows 用干净过滤器栈重建节点

```powershell
# 管理员
pnputil /enum-devices /class USB | findstr /i "05AC"
pnputil /remove-device "USB\VID_05AC&PID_12A8\XXXXXXXX"
# 拔线 → 等 3 秒 → 插回 → 解锁手机点信任
ios.exe list      # 这次应该有 deviceList
```

原状态备份在你自己的工作目录（例如 `Downloads\driver-backup\`）（`enum-key-backup.json`、`usb-composite-device-original.txt`、`enum-composite-device\`），要恢复投屏功能按备份还原。

## 2. wintun.dll：iOS 17+ 的硬门槛

go-ios 的 userspace 隧道要建虚拟网卡走 RSD。缺 `wintun.dll` 就是 `Error loading wintun.dll`，然后**所有**操作失败——包括截图，很容易误判成"设备没连"。

版本用 **0.14.1**（本包 `bin\wintun.dll`），放 `C:\Windows\System32\`（需要管理员）。

## 3. 隧道端口必须避开 Windows 保留段

go-ios 默认 `60105` 落在动态端口范围（49152–65535），Hyper-V / WinNAT 开机就预留了若干块，bind 直接被拒。

```bat
set ENABLE_GO_IOS_AGENT=user
set GO_IOS_AGENT_PORT=28100     :: 49152 以下，不会被预留
bin\ios.exe tunnel start
```

## 4. "WDA 起来就死"不是崩溃，是被回收

现象：脚本里 `admin.up()` 明明成功，脚本一结束 `:8100` 就不可达，`runwda.log` 也没有崩溃栈。

原因：隧道和端口转发是**当前进程的子进程**。父进程退出 → Windows 回收 → 链路消失。

解法：`service.py` —— 调一次 `up()` 然后 `while True: sleep(30)`，把子进程拴在长寿父进程下。`up.cmd` 就是它的启动器。

## 5. SideTap 的两个 Windows bug（本包已绕过）

| Bug | 表现 | 绕过 |
|---|---|---|
| `device._free_port()` | `netstat` 输出解析成 `None` → `AttributeError: 'NoneType' has no attribute 'split'`，链路启动前就崩 | `phone.py`/`service.py` 开头把 `_free_port` 换成容错版 |
| subprocess 用 UTF-8 解码中文输出 | `UnicodeDecodeError: 'utf-8' codec can't decode byte 0xbb` | 同上，包内已处理；上游是硬编码编码问题 |

## 6. 截图坐标不可信（历史最大误区）

早期用投屏快照算坐标：快照 PNG 是 197×428 之类的裁剪/缩放图，跟真实屏幕不是等比的，按钮位置和算出来的坐标差几十像素，点 10 次错 4 次。

**校准证据**：截图里 `1×` 按钮算出来在 x=584，而逻辑屏宽 390×2=780… 比例怎么都对不上；而 OCR 给的 bounds 直接就是 `x=132,y=466`，点下去一次命中。

**结论：坐标只用 accessibility 的 frame（即 `ocr`/`find` 给的 x/y），永远不要从 PNG 反算。**

## 7. 中文名 → bundle id 的坑

`open_app("设置")` 会报 `Unknown app`——因为 `设置` 不在内置映射里，而 `Settings` / `com.apple.Preferences` 在。

稳妥做法：一次性跑 `phone.cmd apps`，把 `{中文名: bundleId}` 存成 json，之后只查表。

## 8. 被 App 楔住（wedge）：不是故障，别重启

抖音的 For You 信息流、某些小程序的 WebView，**永远不响应 iOS accessibility 请求**。WDA 的 `/source` 就会一直挂到超时，看起来像"WDA 死了"。

- 重启 WDA 是**错的**，而且还起不来（旧 runner 还占着，新 runner 报 XCTest error 103）
- 正确姿势：**按 Home** 把那个 App 挪到后台，accessibility 等待立即释放（实测 ~20 秒内 `/status` 恢复）

```bat
phone.cmd home
phone.cmd status
```

## 9. 沙箱 Job Object：分离进程活不过一条命令

在带 kill-on-close Job Object 的宿主里（很多 Agent 框架），`subprocess.Popen(creationflags=DETACHED_PROCESS)` 起的子进程**会被立刻杀掉**——实测连第一行日志都没写出来。

试过但都不通的：`explorer.exe` 拉起、`.vbs`（`cscript`/`wscript` 被当 LOLBin 拦）、`schtasks`（安全策略禁用）。

`phone.py` 的处理：探活 12 秒，进程一死立刻放弃，**降级为"在当前进程内 `admin.up()`"** ——命令一定成功，代价是首条命令 +20 秒，且链路只在这个命令期间有效。
所以：要么宿主支持常驻后台任务，要么用 `up.cmd` 留个窗口。

> 顺带两个副作用，`kitpatch.py` 已经处理：
> · `doctor` 本来会用 `schtasks` 查"签名到期提醒"任务，被拦时刷一屏红色安全告警——现在直接回答"未安装"（那项本来就是建议性质，不影响 PASS）。
> · `start.vbs` 只在**真人双击**时有效（走资源管理器、在用户会话里）；从 Agent 里调 `explorer.exe start.vbs` 会被拦，别指望它。

## 10. 锁屏 / 深睡眠

手机一睡，`ios apps --list` 会返回空——**不要据此判断"WDA 没装"**（SideTap 的 `doctor` 专门区分了这两种情况）。侧键唤醒即可；服务会在 30 秒内自动重连。

## 11. `-20970` / `-69` / `-40` 三个 Sideloadly 错误码

| 码 | 含义 | 处理 |
|---|---|---|
| `-20970` | 登录失败 | 账号密码错；必须走 2FA 验证码；改用开发者账号邮箱 |

## 12. 每次操作都要"重启一次"？那是架构问题不是速度问题

早期实现的问题清单（都已在 `phone.py` 里解决）：

| 旧做法 | 代价 | 新做法 |
|---|---|---|
| 每步起一个新进程/新 MCP 服务 | 3~5 s | 一条命令 = 一个进程，`flow` 多步共用一个进程 |
| 每步 `POST /session` 新建会话 | 1~2 s | 复用 `.state/wda_session` |
| 每步之后 `release_control` | 拆掉采集会话，重建 10.7 s | 默认不释放，只在 `down` 时拆 |
| `sleep 2` 等界面 | 恒定 2 s | `wait_text` / `wait_stable`，典型 0.4~0.8 s |
| 截图 + 人眼找坐标 | 2~5 s 且会点错 | `tap-text` 按标签点，0.4~0.7 s |
| 模型读写整张图 | 上下文暴涨 | `ocr --grep` + `find`，只取需要的几行 |

## 13. 反复掉线的真凶：AppleMobileDeviceService 的配对信任循环（2026-11-11 定案）

**症状**：一晚上掉线 8 次，全在流程中途；`ios list` 变空但 PnP 显示设备 OK；自愈修复后几分钟又掉。

**定位过程**：系统日志（事件 ID 225）显示每次都是 `AppleMobileDeviceService.exe` **主动弹出**设备——同一 PID 每 60~70 秒弹一次，服务根本没重启。这不是线材/电源问题，是服务在**拒绝**这台手机。

**根因**：go-ios 的身份文件被删后重新配对，手机端的信任记录与 Apple usbmuxd 侧的配对记录冲突，服务判定设备不可信 → 弹出强制重配 → 手机重枚举 → 记录依然冲突 → 死循环。删 go-ios 身份文件、`ResetPortEnabled=0`、USB 电源管理，全部治标不治本。

**唯一解法**（验证有效，之后再没掉过）：
1. 拔线
2. 手机：设置 → 通用 → 传输或还原 iPhone → 还原 → **还原位置与隐私**
3. 重插线，解锁，弹「信任此电脑吗」→ 信任
4. PC 侧顺手清一次 `C:/ProgramData/Apple/Lockdown/`（Apple 自己的配对缓存）

**教训**：USB 层的「玄学掉线」，先查事件日志 225；只要 requester 是 AppleMobileDeviceService，直接走信任重置，别再折腾驱动。

## 14. 地图类 App（高德/百度）的 WDA 特性

- 路线规划页、导航页是重型地图页：**无障碍树请求会挂 30 秒**，但截图和 OCR 一直秒回。`wait_text` / `tap_text` 已内置 OCR 降级，无需处理。
- 无障碍树里大量按钮是 `Other` 类型无 frame（如「偏好」），树经常看不到 → OCR 兜底反而更快更准。
- 冷启动有概率卡黑屏开屏：accessibility 树为空、OCR 0 行。按 Home → 重开即可（flow 的 retry 块已内置）。
- 「开始导航」会触发**麦克风权限弹窗**（首次）：`tap_if 不允许` 兜底，已写进示例 flow。
- 高德的 OCR 输出常混着 HTML 片段（`<font size=...>公里`），grep 时记得用「公里」而不是等号匹配。
